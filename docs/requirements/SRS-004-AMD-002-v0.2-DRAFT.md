# SRS-004-AMD-002: Observation record format `AX:OBS:v2`

| Field | Value |
|-------|-------|
| Document ID | SRS-004-AMD-002 |
| Version | 0.2 DRAFT |
| Date | 12 October 2026 |
| Amends | SRS-004 v0.3 by adding a second record format. `AX:OBS:v1` is unchanged and frozen |
| Status | **DRAFT. Drafting approved by the owner 2026-10-12 (PCR-005; PCR-006 v2-only admission preferred). No implementation is authorised.** |
| Related | SRS-004-AMD-001 v1.0 (record size), PCR-004 (identifier and enum rules), PCR-005, PCR-006 |

## 1. Purpose

`AX:OBS:v1` cannot be both RFC 8785 canonical (SHALL-006) and escaped as SHALL-045 requires. It also:
- hashes empty input as 32 zero bytes;
- admits integers outside the I-JSON interoperable range;
- performs an NFC check that is unsound in both directions.

`AX:OBS:v2` fixes these issues under a new identifier, so that no `AX:OBS:v1` record changes meaning and the two can never be confused.

## 2. Version discrimination

**SRS-004-AMD-002-SHALL-001: Identifiers.**
- An `AX:OBS:v2` record SHALL carry `"schema_version": "AX:OBS:v2"`.
- Its commitment SHALL use the tag `AX:OBS:v2`, which SHALL be added to the axioma-spec tag registry (`dvec.h`) before any producer exists.

**SRS-004-AMD-002-SHALL-002: Dispatch.** A verifier SHALL select rules only from `schema_version` and the commitment tag:
- `AX:OBS:v1` records are verified under SRS-004 v0.3 as amended by SRS-004-AMD-001, and never under this amendment;
- `AX:OBS:v2` records are verified under this amendment;
- any other value is `REJECTED(unknown_schema)`;
- a record whose `schema_version` disagrees with the commitment tag of the ledger frame that carries it (the frame's tag field) is `REJECTED(schema_tag_mismatch)`. The tag is not a member of the record;
- a verifier SHALL NOT try both versions and accept whichever matches.

**SRS-004-AMD-002-SHALL-003: v1 preserved.**
- v1 producers, verifiers, golden vectors and records are unchanged.
- No v1 record is rewritten, re-hashed or relabelled as v2.

## 3. Record

**SRS-004-AMD-002-SHALL-004: Members.** A v2 record is a JSON object with exactly these members, in this order (lexicographic by UTF-16 code units, as RFC 8785 requires; all names are ASCII):

| Member | Value |
|---|---|
| `completion_state` | `"COMPLETE"`, `"TRUNCATED"` or `"ERROR"` |
| `failure_type` | `null`, `"TIMEOUT"`, `"INVALID_OUTPUT"` or `"TRANSPORT_ERROR"` |
| `input_hash` | 64 lowercase hex characters (§5) |
| `ledger_seq` | integer, 0 ≤ value ≤ 2^53 − 1 |
| `model_id` | string (§6) |
| `obs_hash` | 64 lowercase hex characters (§5); omitted in the hashed form |
| `oracle_id` | string (§6) |
| `output` | string (§7) |
| `output_size` | integer, 0 ≤ value ≤ 2^53 − 1 |
| `params` | object with members `max_tokens`, `seed`, `temperature`, `top_p`, in that order; each is an integer or `null`. `max_tokens` satisfies 0 ≤ value ≤ 2,147,483,647 (the v1 field width). `seed`, `temperature` and `top_p` satisfy −(2^53 − 1) ≤ value ≤ 2^53 − 1. `temperature` and `top_p` carry the raw signed Q16.16 value as an integer, as in v1 |
| `rejected_record_size` | **only** in records that document a size rejection (SHALL-022); integer, 65,537 ≤ value ≤ 2^53 − 1. Absent from every other record |
| `schema_version` | `"AX:OBS:v2"` |

**SRS-004-AMD-002-SHALL-022: `rejected_record_size`.**
- The member MAY appear only in a record with `completion_state = ERROR`, `failure_type = INVALID_OUTPUT`, `output = ""` and `output_size = 0`.
- Such a record documents that the complete record would have exceeded 65,536 bytes (SRS-004-AMD-001 §2 f). The member records the size the rejected record would have had.
- It SHALL NOT appear in any successful observation record (`COMPLETE`, `TRUNCATED`) or in any other `ERROR` record. Presence elsewhere is `REJECTED(member_not_permitted)`.
- Every member other than those in SHALL-004 is likewise `REJECTED(member_not_permitted)`.

**SRS-004-AMD-002-SHALL-005: Permitted state pairs.** `(completion_state, failure_type)` SHALL be one of:
- `(COMPLETE, null)`;
- `(TRUNCATED, null)`;
- `(ERROR, TIMEOUT)`, `(ERROR, INVALID_OUTPUT)` or `(ERROR, TRANSPORT_ERROR)`.

**SRS-004-AMD-002-SHALL-006: Integers (I-JSON).**
- Every integer SHALL lie within ±(2^53 − 1); `ledger_seq` and `output_size` SHALL also be non-negative.
- Admission SHALL reject an out-of-range value with `REJECTED(integer_range)`; it SHALL NOT clamp or wrap.
- Integers are written in decimal, with a leading `-` for negatives, no `+`, no leading zeros, `0` for zero, and never `-0`.

## 4. Canonical encoding

**SRS-004-AMD-002-SHALL-007: Form.** The canonical form is the RFC 8785 serialisation of the record:
- UTF-8, with no whitespace between tokens;
- members in the SHALL-004 order;
- `null` written as `null`.

**SRS-004-AMD-002-SHALL-008: Strings (RFC 8785 §3.2.2.2).**

| Character | Written as |
|---|---|
| `"` | `\"` |
| `\` | `\\` |
| U+0008 | `\b` |
| U+0009 | `\t` |
| U+000A | `\n` |
| U+000C | `\f` |
| U+000D | `\r` |
| any other U+0000 to U+001F | `\u00xx` with lowercase hex |
| every other character, including U+007F and all non-ASCII | its UTF-8 bytes, unescaped |

Because admission (§7) rejects every control except LF in `output`, and every control in identifiers, in practice only `\"`, `\\` and `\n` occur in admitted records.

## 5. Hashes

**SRS-004-AMD-002-SHALL-009: Input hash.**
- `input_hash` = lowercase hex of SHA-256(input bytes), for every input including the empty one.
- The empty input therefore gives `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.
- This replaces v1's 32 zero bytes, which is a v2-only change, as the owner directed on 2026-10-12.

**SRS-004-AMD-002-SHALL-010: Observation hash.**
- Let `P` be the canonical form of the record with the `obs_hash` member **omitted entirely**: no name, no value, no comma.
- `obs_hash` = lowercase hex of SHA-256(`"AX:OBS:v2"` ‖ LE64(len(P)) ‖ P), where the tag is its 9 ASCII bytes with no terminator and LE64 is the 8-byte little-endian length.
- The stored record is the canonical form with `obs_hash` present.
- A verifier recomputes `P` from the stored record by removing the `obs_hash` member. It SHALL NOT substitute an empty string.

This construction is chosen so that the hashed bytes are a deterministic function of the stored bytes. That is exactly the property finding D-23 shows is missing from `AX:PROOF:v1`.

## 6. Identifiers

**SRS-004-AMD-002-SHALL-011.** `model_id` and `oracle_id` SHALL each be:
- non-empty;
- at most 256 bytes;
- valid UTF-8 in the strict sense of SHALL-012;
- free of U+0000 to U+001F and U+007F to U+009F.

Otherwise the result is `REJECTED(identifier)`. These are the PCR-004 rules; in v2 they are part of the format, not only of admission.

## 7. Output and admission

**SRS-004-AMD-002-SHALL-012.** `output` SHALL be:
- valid UTF-8 (well-formed, shortest form, no surrogates, at most U+10FFFF);
- free of control characters other than U+000A. That is, it contains none of U+0000 to U+0009, U+000B to U+001F, or U+007F to U+009F;
- in NFC as defined in §8.

**SRS-004-AMD-002-SHALL-021: Producer-side transformations.** Before the record is constructed, a producer applies exactly two transformations to the raw oracle output, in this order:
1. **SHALL-043 line endings:** CRLF and lone CR are converted to LF. This is the only text transformation permitted, and it is not a Unicode normalisation.
2. **SHALL-040 truncation:** output longer than `AX_MAX_OUTPUT_BYTES` = 64,512 bytes (`AX_MAX_OBS_BYTES` − 1,024) is cut at that length, at a UTF-8 character boundary, and recorded as `TRUNCATED` with `output_size` set to the converted length before truncation.

Record-level validation (SHALL-020) applies to the record after these steps, so a CR still present in `output` at that point is rejected.

**SRS-004-AMD-002-SHALL-019: Size consistency.**
- For `COMPLETE` and `ERROR` records, `output_size` SHALL equal the byte length of `output`.
- For `TRUNCATED` records, it SHALL be strictly greater than that length: it records the original size, and a truncated record has lost bytes (SHALL-040). v1 accepted equality; v2 does not.
- Otherwise the result is `REJECTED(output_size)`.

**SRS-004-AMD-002-SHALL-013.** SRS-004-SHALL-040 (truncation of raw output above `AX_MAX_OUTPUT_BYTES`, recorded as TRUNCATED) and SRS-004-AMD-001 (65,536-byte limit on the complete stored record, with rejection) apply unchanged to v2 records.

**SRS-004-AMD-002-SHALL-014.** `input == NULL` with a non-zero length SHALL be rejected (`REJECTED(input)`). The empty input is admissible.

## 8. NFC (PCR-006 Option B, v2 only)

**SRS-004-AMD-002-SHALL-015: Unicode version.** NFC is defined by UAX #15 and the Unicode Character Database **version 16.0.0**. Changing the version requires a new record format version or an explicit amendment.

**SRS-004-AMD-002-SHALL-016: Verification, not normalisation.** A string `s` is admissible only if all of the following hold:
1. `toNFC(s) = s`, by UCD 16.0.0;
2. **bound:** `toNFD(s)` contains no run of more than **30** consecutive code points whose Canonical_Combining_Class is non-zero, which is the limit of the UAX #15 Stream-Safe Text Format applied to the canonical decomposition.

Otherwise the result is `REJECTED(not_nfc)` or `REJECTED(nfc_bound)`.

Admission SHALL NOT apply Unicode normalisation, repair or substitute text. The SHALL-043 line-ending conversion of SHALL-021 is not a Unicode normalisation and is unaffected. In v2 the NFC requirement applies to `output`; identifiers are governed by SHALL-011.

Implementations MAY use any algorithm. The informative strategy is:
- run the quick check on every code point;
- reject on No;
- run a full composition check, in fixed memory, on segments that contain Maybe.

The bound guarantees that every segment fits a fixed buffer.

**SRS-004-AMD-002-SHALL-017: Conformance.** An NFC implementation SHALL be tested against all three of the following:
1. the NFC column of UCD 16.0.0 `NormalizationTest.txt`. A line is admissible only where `c2 = c1`; otherwise it SHALL be rejected;
2. every assigned single code point;
3. the targeted set in `SRS-004-AMD-002-vectors/nfc/`. It covers:
   - Indic scripts: Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada and Malayalam, including nukta forms and two-part vowel signs;
   - Hangul jamo sequences;
   - canonical reordering cases;
   - runs of 30 and 31 non-starters.

The reference SHALL be an implementation independent of the one under test, at the same Unicode version.

## 9. Rejection verdicts

`REJECTED(` followed by one of these reasons and `)`:

| Reason | Applies to |
|---|---|
| `unknown_schema` | `schema_version` not recognised (SHALL-002) |
| `schema_tag_mismatch` | `schema_version` and commitment tag disagree (SHALL-002) |
| `state_pair` | `(completion_state, failure_type)` not permitted, or out of enum (SHALL-005) |
| `member_not_permitted` | a member outside SHALL-004, or `rejected_record_size` where SHALL-022 does not permit it |
| `integer_range` | an integer member outside its own range in SHALL-004 (the general bound of SHALL-006, or the tighter `max_tokens` and `rejected_record_size` bounds), or a value that is not an integer where one is required (`null` only where SHALL-004 permits it) |
| `identifier` | `model_id` or `oracle_id` fails SHALL-011 |
| `input` | NULL input with non-zero length (SHALL-014) |
| `output_encoding` | output not valid UTF-8, or contains a forbidden control character (SHALL-012) |
| `output_size` | `output_size` inconsistent with `output` (SHALL-019) |
| `not_nfc` | output fails §8 condition 1 |
| `nfc_bound` | output fails §8 condition 2 |
| `record_size` | stored record over 65,536 bytes, measured as in SRS-004-AMD-001 §2(a): canonical bytes with `obs_hash` present, excluding framing |
| `v1_after_cutover`, `v2_before_cutover` | version outside its activation window (SHALL-025); verification of stored records only |

**SRS-004-AMD-002-SHALL-020: Check order.** Admission applies the checks in the order below and reports the first that fails, so that every malformed input has exactly one reason:
1. `state_pair`
2. `member_not_permitted`
3. `integer_range`, checking `ledger_seq`, `output_size`, then `params` members in order, then `rejected_record_size`
4. `identifier`, checking `model_id`, then `oracle_id`
5. `input`
6. `output_encoding`
7. `output_size`
8. `not_nfc`
9. `nfc_bound`
10. `record_size`: after steps 1 to 9 pass, compute `input_hash` and `obs_hash`, build the stored record, and reject it if it is longer than 65,536 bytes (65,536 is admissible)

`unknown_schema` and `schema_tag_mismatch` apply to verification of stored records.

## 10. Activation (cut-over), rollback and migration

**SRS-004-AMD-002-SHALL-023: Activation.**
- Production of `AX:OBS:v2` begins only by an explicit owner-approved activation decision. It is never inferred from a calendar date, a software version or the presence of v2 records.
- The decision is recorded on the ledger in the same way as SRS-007-AMD-003 SHALL-007 and SHALL-008: an `AX:STATE:v1` version activation record with the following members:
  - `activation_id`;
  - `component`;
  - `from_version` `AX:OBS:v1`;
  - `to_version` `AX:OBS:v2`;
  - the Unicode version (16.0.0);
  - `decision_ref`, the SHA-256 of the written owner decision;
  - `config_hash`.
- Its ledger sequence number opens the v2 window.

**SRS-004-AMD-002-SHALL-024: Rollback.** Rollback is a separate owner decision, recorded as a version rollback record. Records already emitted are never deleted, rewritten or relabelled. v2 records emitted inside a window remain valid v2.

**SRS-004-AMD-002-SHALL-025: Verifiers.**
- Verifiers accept both versions indefinitely, each under its own rules, and determine the expected version per ledger position from the activation and rollback records.
- A v1 observation inside a v2 window is `REJECTED(v1_after_cutover)`, and a v2 observation outside one is `REJECTED(v2_before_cutover)`.
- An activation record without a `decision_ref` opens no window.

SDK builders that emit records labelled `AX:OBS:v1` with a different schema (finding F-12) are withdrawn, not relabelled.

## 11. Conformance vectors

**SRS-004-AMD-002-SHALL-018.** Before any implementation is accepted, the vector set of `SRS-004-AMD-002-vectors/VECTOR-FORMAT.md` SHALL be produced byte-identically by at least two implementations written independently from this text in different languages. The NFC vectors (§8) are produced separately against a Unicode 16.0.0 reference.
