## 1. Reason for amendment

SRS-007-SHALL-059 (v0.3) specifies an evidence-closure Merkle tree with these properties:
- leaves are the raw evidence hashes;
- internal nodes are `SHA-256(left ‖ right)`;
- the last node is duplicated on odd levels;
- the empty root is 32 zero bytes.

Independent reproduction at axioma-governance `93d75a6e3e9558f1ce7e7763da6defdc56fe1371` showed that this construction, implemented as specified, admits the following:
- an internal node accepted as a member leaf;
- a valid path accepted for any claimed leaf index;
- identical roots for `{a,b,c}` and `{a,b,c,c}`, and for 5, 6 and 8 leaves when the last item repeats;
- a closure check that passes for a stored report edited to append a duplicate of its largest item.

These defects are properties of the specification, not only of the code. A corrected construction therefore cannot honestly carry the v0.3 identifier. This amendment freezes the v0.3 construction as **v1** and defines **`AX:MERKLE:v2`**.

## 2. Scope of assurance (normative)

**SRS-007-AMD-001-SHALL-001.** A valid `AX:MERKLE:v2` closure root or inclusion proof establishes only these two things:
- the committed set of evidence references is exactly the ordered list of `n` 32-byte values from which the root was computed;
- a given reference is a member of that list at a given index.

It does **not** establish:
- that any evidence item is true, complete or authorised;
- that the evidence set is complete with respect to any external event;
- that any policy or regulatory requirement is met;
- that the root itself is authentic. Authenticity requires a separately authenticated root (signature or external anchor); see DR-000.

Documents, interfaces and reports SHALL NOT describe a closure root or inclusion proof as proof of truth, compliance or completeness.

## 3. Definitions

- `‖` is byte concatenation.
- `SHA-256` is FIPS 180-4 SHA-256 and produces 32 bytes.
- `LE64(x)` is the unsigned 64-bit little-endian encoding of `x` (8 bytes).
- `TAG` is the 12 ASCII bytes `AX:MERKLE:v2` (0x41 0x58 0x3A 0x4D 0x45 0x52 0x4B 0x4C 0x45 0x3A 0x76 0x32), with no terminator and no length prefix.
- A **reference** is exactly 32 bytes.
- `N_MAX = 1024`.

## 4. Construction

**SRS-007-AMD-001-SHALL-002: Input list.** The input is a list `D = [d_0 … d_{n-1}]` of `n` references with `0 ≤ n ≤ N_MAX`. `D` SHALL be **strictly ascending** under bytewise unsigned comparison (`memcmp` order). An implementation SHALL reject, not repair, a list that:
- is not ascending;
- contains two equal references;
- has `n > N_MAX`.

Producers SHALL sort before submission. Implementations SHALL NOT deduplicate silently.

Checks SHALL be applied in this order, so that nothing beyond `N_MAX` is read:
1. `n > N_MAX` gives `REJECTED(too_many_refs)`.
2. Any element of the wrong length gives `REJECTED(malformed_reference)`.
3. Any adjacent pair with `d_i ≥ d_{i+1}`, which includes equal references, gives `REJECTED(input_not_strictly_ascending)`.

**SRS-007-AMD-001-SHALL-003: Leaf and node hashes.**
```
leaf_hash(d)    = SHA-256(0x00 ‖ d)              -- 33-byte input
node_hash(l, r) = SHA-256(0x01 ‖ l ‖ r)          -- 65-byte input
```

**SRS-007-AMD-001-SHALL-004: Merkle tree hash.** For `n ≥ 1`, following RFC 9162 §2.1.1 (no node duplication):
```
MTH([d_0])        = leaf_hash(d_0)
MTH(D[0:n]), n>1  = node_hash( MTH(D[0:k]), MTH(D[k:n]) )
                    where k is the largest power of two strictly less than n
```

**SRS-007-AMD-001-SHALL-005: Closure root (size-bound and tagged).**
```
closure_root(D) = SHA-256( TAG ‖ LE64(n) ‖ MTH(D) )     for n ≥ 1
closure_root([]) = SHA-256( TAG ‖ LE64(0) )             for n = 0
```

## 5. Inclusion proofs

**SRS-007-AMD-001-SHALL-006: Proof object.** An inclusion proof is the tuple `(leaf_index m, tree_size n, path [p_1 … p_L])`, where each `p_i` is 32 bytes. Proofs for `n = 0` do not exist.

**SRS-007-AMD-001-SHALL-007: Path generation.** Following RFC 9162 §2.1.3.1:
```
PATH(m, [d_0])           = []
PATH(m, D[0:n]), n > 1   = PATH(m, D[0:k])   ‖ [ MTH(D[k:n]) ]   if m < k
                         = PATH(m-k, D[k:n]) ‖ [ MTH(D[0:k]) ]   if m ≥ k
                           (k as in SHALL-004; ‖ here is list append)
```

**SRS-007-AMD-001-SHALL-008: Path verification.** Given reference `d`, proof `(m, n, path)` and an expected `closure_root R`, a verifier SHALL return VERIFIED only if all of the following hold:
```
0. len(d) = 32 and every p_i is 32 bytes else REJECTED(malformed_reference)
1. 1 ≤ n ≤ N_MAX and 0 ≤ m < n          else REJECTED(index_or_size)
1b. L ≤ 10                               else REJECTED(path_too_long)   -- before any p_i is read
2. fn := m ; sn := n - 1 ; r := leaf_hash(d)
3. for each p in path, in order:
     if sn = 0: REJECTED(path_too_long)
     if (fn & 1) = 1 or fn = sn:
         r := node_hash(p, r)
         while (fn & 1) = 0 and fn ≠ 0:
             fn := fn >> 1 ; sn := sn >> 1
     else:
         r := node_hash(r, p)
     fn := fn >> 1 ; sn := sn >> 1
4. if sn ≠ 0: REJECTED(path_too_short)
5. if SHA-256(TAG ‖ LE64(n) ‖ r) ≠ R: REJECTED(root_mismatch)
6. VERIFIED
```
The path length is fully determined by `m` and `n`. For `n ≤ N_MAX` it never exceeds 10, and step 1b rejects a longer path before reading it. Verification SHALL NOT read memory beyond the supplied path length.

## 6. Carriage and versioning

**SRS-007-AMD-001-SHALL-009.** A v2 closure root SHALL be carried only in an `AX:PROOF:v2` record, which SHALL contain at least:
- `"closure_alg": "AX:MERKLE:v2"`;
- `"closure_size": n` (JSON integer);
- `"evidence_closure_root": <64 lowercase hex characters>`.

A v2 root SHALL NOT appear in an `AX:PROOF:v1` record or in any field whose schema does not name its construction.

**SRS-007-AMD-001-SHALL-010: v1 frozen.** The v0.3 SHALL-059 construction is designated `AX:MERKLE:v1` and is frozen. No producer SHALL emit new v1 closure roots or v1 inclusion proofs after the owner-approved cut-over date. Existing v1 records SHALL NOT be rewritten.

**SRS-007-AMD-001-SHALL-011: Amendment to SHALL-056 rule 3.** For evidence-closure material, rule 3 ("v1 proofs remain valid in v2 systems") is amended as follows:
- A v2 system given a v1 closure root and the complete leaf list MAY recompute it, and SHALL report `V1_ROOT_RECOMPUTED` with the caveat that duplicate-leaf and leaf-count ambiguity cannot be excluded.
- A v2 system given a v1 inclusion proof SHALL report `V1_PROOF_UNSOUND` and SHALL NOT report it as VERIFIED.

**SRS-007-AMD-001-SHALL-012: Verdicts.** The closed set below applies to construction (SHALL-002, SHALL-005, SHALL-007) and to verification (SHALL-008) alike:
- `VERIFIED`
- `REJECTED(index_or_size | path_too_long | path_too_short | root_mismatch | input_not_strictly_ascending | too_many_refs | malformed_reference)`
- `V1_ROOT_RECOMPUTED`
- `V1_PROOF_UNSOUND`

The two V1 verdicts belong to v1-aware verifiers and are outside the v2 conformance vector set. Their input contract (how a verifier recognises v1 material) is to be fixed in the `AX:PROOF:v2` schema document.

## 7. Conformance vectors

**SRS-007-AMD-001-SHALL-013.** Before any implementation is accepted, a vector set SHALL be generated by at least two implementations written independently from this text in different languages, and SHALL be byte-identical between them. It SHALL cover:
- n ∈ {0, 1, 2, 3, 4, 5, 7, 8, 9, 1024};
- every leaf index for n ≤ 9, plus indices 0, 511, 512 and 1023 for n = 1024;
- rejection cases:
  - an internal node presented as a leaf;
  - a wrong leaf index;
  - a wrong tree size;
  - a path one element short and one element long;
  - a path longer than 10;
  - a root computed for a different n;
  - a duplicate reference;
  - a non-ascending list;
  - n = 1025.

**Status at v0.2.** A vector set was generated by two implementations written independently from the v0.1 text, one in stdlib Python and one in C99 with its own FIPS 180-4 SHA-256. Neither implementer had access to any existing Merkle or SHA-256 code in the estate, or to the other's work. The two outputs are byte-identical: 65 lines, SHA-256 `96e66cd14f39972fc79444498407f0f4fca37bb2de82dfad9e2840bd8f0a4efd`. The v0.2 clarifications (check order, `malformed_reference`, step 1b) codify the behaviour both implementations had independently chosen, and change no vector. Files are in `SRS-007-AMD-001-vectors/`.

Known gap: rejection case `internal_node_as_leaf_short` is rejected by path length before the 0x00/0x01 separation is exercised. Case `internal_node_as_leaf_n2` exercises the separation. Add a case with a correct-length path in v0.3.

v1 vectors (axioma-sdk `golden/merkle/merkle_4leaf.hex` and `merkle_7leaf.hex`) are retained unchanged and labelled v1.
