## 1. Reason for amendment

SRS-007-SHALL-059 (v0.3) specifies an evidence-closure Merkle tree with these properties:
- leaves are the raw evidence hashes;
- internal nodes are `SHA-256(left ‖ right)`;
- the last node is duplicated on odd levels;
- the root of a single-leaf tree is the leaf itself;
- the empty root is 32 zero bytes.

Independent reproduction at axioma-governance `93d75a6e3e9558f1ce7e7763da6defdc56fe1371` showed that this construction, implemented as specified, admits the following:
- an internal node accepted as a member leaf;
- a valid path accepted for any claimed leaf index;
- identical roots for `{a,b,c}` and `{a,b,c,c}`, and for 5, 6 and 8 leaves when the last item repeats;
- a closure check that passes for a stored report edited to append a duplicate of its largest item.

These defects are properties of the specification, not only of the code. A corrected construction therefore cannot honestly carry the v0.3 identifier. This amendment freezes the v0.3 construction as **`AX:MERKLE:v1`** (Appendix A) and defines **`AX:MERKLE:v2`**.

## 2. Scope of assurance (normative)

**SRS-007-AMD-001-SHALL-001.** A valid `AX:MERKLE:v2` closure root or inclusion proof establishes only these two things:
- the committed set of evidence references is exactly the strictly ascending list of `n` 32-byte values from which the root was computed;
- a given reference is a member of that list at a given index.

It does **not** establish any of the following:
- that any evidence item is true, complete or authorised;
- that the evidence set is complete with respect to any external event;
- that any policy or regulatory requirement is met;
- that the root itself is authentic. Authenticity requires a separately authenticated root (signature or external anchor); see DR-000.

Documents, interfaces and reports SHALL NOT describe a closure root or inclusion proof as proof of truth, compliance or completeness.

## 3. Definitions

- `‖` is byte concatenation.
- `SHA-256` is FIPS 180-4 SHA-256 and produces 32 bytes.
- `LE64(x)` is the unsigned 64-bit little-endian encoding of `x` (8 bytes).
- `TAG` is the 12 ASCII bytes `AX:MERKLE:v2` (0x41 0x58 0x3A 0x4D 0x45 0x52 0x4B 0x4C 0x45 0x3A 0x76 0x32), with no terminator and no length prefix.
- A **reference** is exactly 32 bytes. References are opaque: this construction does not interpret or re-derive them.
- `N_MAX = 1024`.
- Byte strings are compared bytewise as unsigned values (`memcmp` order). `a < b` means `a` sorts strictly before `b`.

## 4. Construction

### 4.1 Domain separation

**SRS-007-AMD-001-SHALL-003: Hash domains.** Every SHA-256 evaluation in this construction falls in exactly one of three domains, distinguished by a prefix that no other domain uses at the same position:

| Domain | Input | Input length | Distinguishing prefix |
|---|---|---|---|
| Leaf | `0x00 ‖ d` | 33 bytes | first byte 0x00 |
| Internal node | `0x01 ‖ l ‖ r` | 65 bytes | first byte 0x01 |
| Closure root | `TAG ‖ LE64(n) ‖ MTH(D)`, or `TAG ‖ LE64(0)` when `n = 0` | 52 or 20 bytes | first 12 bytes are TAG, whose first byte is 0x41 (`A`) |

```
leaf_hash(d)    = SHA-256(0x00 ‖ d)
node_hash(l, r) = SHA-256(0x01 ‖ l ‖ r)
```

Consequences, stated so that they can be tested:
- A leaf hash cannot equal an internal-node hash, and a closure root cannot equal either, except by a SHA-256 collision between inputs that differ in their first byte.
- An internal node therefore cannot be presented as a member reference (vectors 1, 2 and 13).
- A v2 closure root cannot equal any v1 value except by such a collision. A v1 root is either a raw reference, 32 zero bytes, or SHA-256 of a 64-byte input (vector 14).

### 4.2 Input list, canonical ordering and duplicates

**SRS-007-AMD-001-SHALL-002: Input list.** The input is a list `D = [d_0 … d_{n-1}]` of `n` references with `0 ≤ n ≤ N_MAX`. An implementation SHALL reject, not repair, a list that fails any of the checks below. They SHALL be applied in this order, so that nothing beyond `N_MAX` is read:
1. `n > N_MAX`: `REJECTED(too_many_refs)`.
2. Any element not exactly 32 bytes: `REJECTED(malformed_reference)`.
3. Any adjacent pair with `d_i ≥ d_{i+1}`, which includes two equal references: `REJECTED(input_not_strictly_ascending)`.

**SRS-007-AMD-001-SHALL-014: Canonical leaf ordering.** The closure commits to a **set** of references, encoded in its single canonical order, strictly ascending bytewise.
- A producer SHALL sort a copy of the references and pass the sorted list to the construction. The construction (`closure_root`, SHALL-005) takes its input exactly as given and never sorts it.
- The order in which references appear elsewhere in a record is presentation only and SHALL NOT affect the root. This covers, for example, an `evidence_ordering` of TEMPORAL or DECLARED.
- Two producers given the same set SHALL obtain the same root whatever order they received it in.
- A verifier SHALL NOT sort input supplied to it as a closure list. It SHALL reject an unsorted list under SHALL-002 step 3.

**SRS-007-AMD-001-SHALL-015: Duplicates.**
- A set has no duplicates. A producer whose evidence collection contains the same reference twice SHALL NOT submit both copies. It SHALL either reject the collection or record the deduplication explicitly, outside the closure, in the carrying record.
- The construction itself never deduplicates (SHALL-002 step 3).
- A verifier holding the full list SHALL recheck SHALL-002 before recomputing the root.

### 4.3 Tree hash and root

**SRS-007-AMD-001-SHALL-004: Merkle tree hash.** For `n ≥ 1`, following RFC 9162 §2.1.1 (no node duplication):
```
MTH([d_0])        = leaf_hash(d_0)
MTH(D[0:n]), n>1  = node_hash( MTH(D[0:k]), MTH(D[k:n]) )
                    where k is the largest power of two strictly less than n
```

**SRS-007-AMD-001-SHALL-005: Closure root (size-bound and tagged).**
```
closure_root(D)  = SHA-256( TAG ‖ LE64(n) ‖ MTH(D) )     for n ≥ 1
closure_root([]) = SHA-256( TAG ‖ LE64(0) )             for n = 0
```

## 5. Inclusion proofs

**SRS-007-AMD-001-SHALL-006: Proof object.** An inclusion proof is the tuple `(leaf_index m, tree_size n, path [p_1 … p_L])`, where each `p_i` is 32 bytes. Proofs for `n = 0` do not exist.

**SRS-007-AMD-001-SHALL-007: Path generation.** Path generation SHALL apply the SHALL-002 checks to `D`. It SHALL return `REJECTED(index_or_size)` unless `0 ≤ m < n`. Otherwise, following RFC 9162 §2.1.3.1:
```
PATH(m, [d_0])           = []
PATH(m, D[0:n]), n > 1   = PATH(m, D[0:k])   ‖ [ MTH(D[k:n]) ]   if m < k
                         = PATH(m-k, D[k:n]) ‖ [ MTH(D[0:k]) ]   if m ≥ k
                           (k as in SHALL-004; ‖ here is list append)
```

**SRS-007-AMD-001-SHALL-016: Tree-size binding.** The tree size is bound twice:
- into the root, by `LE64(n)` (SHALL-005);
- against the record that carries the root, by the expected size `N`, which is that record's `closure_size`.

A verifier SHALL take `N` from the carrying record, never from the proof alone, and SHALL reject a proof whose `n ≠ N` before reading the path (SHALL-008 step 1a).

**SRS-007-AMD-001-SHALL-008: Path verification.** Given:
- a reference `d`;
- a proof `(m, n, path)`;
- an expected closure root `R`;
- an expected size `N`;

a verifier SHALL return VERIFIED only if all the steps below pass, applied in this order:
```
0.  len(d) = 32 and every p_i is 32 bytes   else REJECTED(malformed_reference)   -- lengths only
1.  1 ≤ n ≤ N_MAX and 0 ≤ m < n             else REJECTED(index_or_size)
1a. n = N                                   else REJECTED(size_mismatch)
1b. L ≤ 10                                  else REJECTED(path_too_long)   -- before the contents of any p_i are read
2.  fn := m ; sn := n - 1 ; r := leaf_hash(d)
3.  for each p in path, in order:
      if sn = 0: REJECTED(path_too_long)
      if (fn & 1) = 1 or fn = sn:
          r := node_hash(p, r)
          while (fn & 1) = 0 and fn ≠ 0:
              fn := fn >> 1 ; sn := sn >> 1
      else:
          r := node_hash(r, p)
      fn := fn >> 1 ; sn := sn >> 1
4.  if sn ≠ 0: REJECTED(path_too_short)
5.  if SHA-256(TAG ‖ LE64(n) ‖ r) ≠ R: REJECTED(root_mismatch)
6.  VERIFIED
```
- The leaf index is never trusted for direction. Direction at every level is derived from `(m, n)`, so a valid path for index `m` does not verify at any other index (vector 3).
- The path length is fully determined by `m` and `n`. For `n ≤ N_MAX` it never exceeds 10, and step 1b rejects a longer path before reading it.
- Verification SHALL NOT read memory beyond the supplied path length.
- Step 0 inspects only the length of each supplied element, never its contents. `malformed_reference` covers a reference or a path element of the wrong length.

## 6. Carriage and version discrimination

**SRS-007-AMD-001-SHALL-009: Carriage.** A v2 closure root SHALL be carried only in an `AX:PROOF:v2` record, which SHALL contain at least:
- `"closure_alg": "AX:MERKLE:v2"`;
- `"closure_size": n` (JSON integer, 0 ≤ n ≤ N_MAX);
- `"evidence_closure_root": <64 lowercase hex characters>`.

A v2 root SHALL NOT appear in an `AX:PROOF:v1` record or in any field whose schema does not name its construction. The full `AX:PROOF:v2` schema is a companion document and is outside this amendment (§9).

**SRS-007-AMD-001-SHALL-017: Version discrimination.** A verifier SHALL select the construction only from explicit identifiers, never from the shape or value of a root:
1. A record whose `schema_version` is `AX:PROOF:v2` SHALL carry `closure_alg`.
   - If `closure_alg` is `AX:MERKLE:v2`, v2 rules apply.
   - If it is any other value, or absent, the verdict is `REJECTED(unknown_construction)`.
2. Closure material in an `AX:PROOF:v1` record, or in a compliance report whose schema predates this amendment, is **v1 material** by schema. It is evaluated only under SHALL-011, and SHALL NOT be relabelled, re-encoded or reinterpreted as v2.
3. Material whose schema identifies neither construction is `REJECTED(unknown_construction)`. A verifier SHALL NOT try both constructions and accept whichever matches.

**SRS-007-AMD-001-SHALL-010: v1 frozen.**
- The v0.3 SHALL-059 construction, restated exactly in Appendix A, is designated `AX:MERKLE:v1` and is frozen.
- No producer SHALL emit new v1 closure roots or v1 inclusion proofs after the owner-approved cut-over date.
- Existing v1 records are historical evidence. They SHALL NOT be rewritten, re-rooted or relabelled as v2.

**SRS-007-AMD-001-SHALL-011: Amendment to SHALL-056 rule 3.** For evidence-closure material, rule 3 ("v1 proofs remain valid in v2 systems") is amended as follows:
- A v2 system given a v1 closure root and the complete leaf list MAY recompute it under Appendix A. It SHALL report `V1_ROOT_RECOMPUTED` with the caveat that duplicate-leaf and leaf-count ambiguity cannot be excluded.
- A v2 system given a v1 inclusion proof SHALL report `V1_PROOF_UNSOUND` and SHALL NOT report it as VERIFIED.

**SRS-007-AMD-001-SHALL-012: Verdicts.** The closed set below applies to construction (SHALL-002, SHALL-005, SHALL-007) and to verification (SHALL-008) alike:
- `VERIFIED`
- `REJECTED(index_or_size | size_mismatch | path_too_long | path_too_short | root_mismatch | input_not_strictly_ascending | too_many_refs | malformed_reference)`
- `REJECTED(unknown_construction)`: record-level dispatch only (SHALL-017)
- `V1_ROOT_RECOMPUTED`
- `V1_PROOF_UNSOUND`

A successful construction or path generation yields the root or path itself; the `REJECTED` verdicts above are its failure results. The two V1 verdicts and `unknown_construction` belong to record-level verifiers. They are outside the Merkle conformance vector set until the `AX:PROOF:v2` schema exists.

## 7. Conformance vectors

**SRS-007-AMD-001-SHALL-013.** Before any implementation is accepted, a vector set SHALL be generated by at least two implementations written independently from this text, in different languages, and SHALL be byte-identical between them. It SHALL cover:
- n ∈ {0, 1, 2, 3, 4, 5, 7, 8, 9, 1024};
- every leaf index for n ≤ 9, plus indices 0, 511, 512 and 1023 for n = 1024;
- rejection cases:
  - an internal node presented as a leaf, with a short path, at a smaller tree size, and with a path of the correct length;
  - a wrong leaf index;
  - a wrong tree size;
  - a path one element short and one element long;
  - a path longer than 10;
  - a root computed for a different n;
  - an out-of-range index;
  - a duplicate reference;
  - a non-ascending list;
  - n = 1025;
  - a v1 root presented as a v2 root;
  - a proof size differing from the carrying record's size;
- v1 reference roots under Appendix A for n ∈ {0, 1, 2, 3, 4, 5}, so that v1 material can be recomputed consistently and is never confused with v2.

The harness is `SRS-007-AMD-001-vectors/VECTOR-FORMAT.md`. Lines carried over from v0.2 SHALL remain byte-identical.

v1 vectors (axioma-sdk `golden/merkle/merkle_4leaf.hex` and `merkle_7leaf.hex`) are retained unchanged and labelled v1.

## Appendix A: `AX:MERKLE:v1` (frozen; restated from SRS-007 v0.3 SHALL-059 and the reference implementation at axioma-governance `93d75a6`)

For a strictly ascending list `D` of `n` references:
```
V1_ROOT([])        = 32 zero bytes
V1_ROOT([d_0])     = d_0                                   (no hashing)
V1_ROOT(D), n ≥ 2  : level := D
                     while len(level) > 1:
                         if len(level) is odd: append a copy of level's last element
                         level := [ SHA-256(level[2i] ‖ level[2i+1]) for i = 0 .. len(level)/2 - 1 ]
                     V1_ROOT = level[0]
```
- Recomputation takes the list exactly as stored and applies no v2 input checks. v1 itself rejected only descending input and accepted duplicates, which is part of its defect.
- For the sorted lists D_0 to D_5 of the vector harness, this restatement reproduces axioma-governance `ax_merkle_compute_root` at `93d75a6` byte for byte (V1ROOT lines).
- This appendix exists only so that historical v1 material can be recomputed (SHALL-011) and recognised. It is not a construction any producer may adopt.
