## 1. Finding

The `AX:PROOF:v1` producer computes `proof_hash` and `commitment` while the record's `commitment` member holds 32 zero bytes. It then stores the real commitment in that member. The canonical form includes `commitment`, so the stored record never re-serialises to the bytes that were hashed. A verifier that serialises the stored record as given, such as `ax_proof_verify_hash`, reports a mismatch for **every** finalised record. This is reproduced on pristine `main` `93d75a6`.

## 2. Decision

- v1 producer bytes are preserved.
- Stored v1 records are verified under an explicit legacy profile that reproduces the producer's calculation.
- The correct construction, with members excluded from the hashed form, is specified for `AX:PROOF:v2` in SRS-007-AMD-003 §3.

## 3. Requirements

**SRS-007-AMD-004-SHALL-001: Legacy profile.** A verifier of a stored `AX:PROOF:v1` record SHALL compute, on a copy of the record whose `commitment` member is set to 32 zero bytes:
1. `H` = SHA-256(canonical form without `proof_hash`);
2. `C` = SHA-256(`"AX:PROOF:v1"` ‖ LE64(len(P)) ‖ P), where P is the canonical form with `proof_hash` included.

The stored record is consistent only if `H` equals the stored `proof_hash` **and** `C` equals the stored `commitment`.

**SRS-007-AMD-004-SHALL-002: Order and verdicts.** The verifier SHALL first apply the structural checks (§3 SHALL-003). It SHALL then report exactly one of these verdicts:

| Verdict | Meaning |
|---|---|
| `V1_LEGACY_CONSISTENT` | both stored hashes reproduce |
| `V1_LEGACY_HASH_MISMATCH` | `proof_hash` does not reproduce. The commitment is not evaluated |
| `V1_LEGACY_COMMITMENT_MISMATCH` | `proof_hash` reproduces and `commitment` does not |
| `V1_LEGACY_STRUCTURE_INVALID` | structural checks failed. No hash is evaluated |

**SRS-007-AMD-004-SHALL-003: Structural checks.** A record is structurally valid only if all of the following hold:
- the required members are present (SRS-007-SHALL-004);
- `claim` and `rule_id` are non-empty;
- at least one evidence reference is present;
- a `proof_hash` is present;
- every enumerated value is in range;
- every string is terminated within its field;
- the canonical form fits the 16,384-byte serialisation buffer.

The producer limit of 192 references (SRS-007-AMD-002) does **not** apply. Records of 193 to 237 references produced before that amendment remain eligible.

**SRS-007-AMD-004-SHALL-004: Consistency is not provenance.**
- `V1_LEGACY_CONSISTENT` establishes only that the stored hashes are those a v1 producer would compute for the stored content.
- It SHALL NOT be reported or displayed as VERIFIED, authentic or proven.
- Anyone can construct a consistent record.
- Provenance requires a separately authenticated chain head or signature (DR-000; SRS-007-AMD-001 SHALL-001).
- A verdict display SHALL state "hash-consistent (legacy v1 profile); provenance not established" or equivalent.

**SRS-007-AMD-004-SHALL-005: No rewriting.** Stored v1 records SHALL NOT be re-hashed, corrected or rewritten to make the as-given serialisation consistent.

**SRS-007-AMD-004-SHALL-006: Existing function.** `ax_proof_verify_hash` keeps its behaviour, which is a mismatch for finalised records. It SHALL be documented as unsuitable for stored records. It SHALL NOT be used to report a verdict on stored v1 records.
