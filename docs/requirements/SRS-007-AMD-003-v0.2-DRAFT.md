## 1. Purpose

SRS-007-AMD-001 allows a v2 closure root only in an `AX:PROOF:v2` record and defers the record schema to this document. This document also:
- fixes how a verifier recognises legacy v1 material;
- fixes how producers cut over;
- avoids, by construction, the hash-coverage defect D-23 found in `AX:PROOF:v1`.

## 2. Record

**SRS-007-AMD-003-SHALL-001: Members.** An `AX:PROOF:v2` record is a JSON object with exactly these members, in RFC 8785 order. The canonical encoding is RFC 8785, with string escaping exactly as SRS-004-AMD-002 SHALL-008 specifies.

| Member | Value |
|---|---|
| `claim` | string, 1 to 255 bytes, UTF-8, no U+0000 to U+001F or U+007F to U+009F |
| `closure_alg` | `"AX:MERKLE:v2"` |
| `closure_size` | integer, 1 ≤ n ≤ 1,024 (SRS-007-AMD-001 N_MAX); a proof without evidence is not admissible (SHALL-006) |
| `commitment` | 64 lowercase hex characters (§3) |
| `evidence_closure_root` | 64 lowercase hex characters: `closure_root(evidence_refs)` per SRS-007-AMD-001 SHALL-005 |
| `evidence_order` | `null` for lexicographic presentation, or an array of `closure_size` distinct integers, a permutation of 0 … n−1, giving the presentation order (§2.1) |
| `evidence_refs` | array of `closure_size` strings, each 64 lowercase hex characters, **strictly ascending** (SRS-007-AMD-001 SHALL-002, SHALL-014) |
| `ledger_seq` | integer, 0 ≤ value ≤ 2^53 − 1 |
| `ordering_metadata` | `null` if `evidence_order` is `null`; otherwise an object with `description` (at most 127 bytes), `direction` (at most 15 bytes) and `key_field` (at most 31 bytes). These follow the same character rules as `claim` |
| `prev_chain_head` | 64 lowercase hex characters |
| `proof_hash` | 64 lowercase hex characters (§3) |
| `proof_type` | one of the seven v1 proof types |
| `result` | `"VALID"`, `"INVALID"` or `"INTEGRITY_FAULT"` |
| `rule_id` | string, 1 to 63 bytes, same character rules as `claim` |
| `schema_version` | `"AX:PROOF:v2"` |
| `violation` | `null` when `result` is `VALID`; otherwise one of the eight v1 violation names, or `null` |

### 2.1 Proof ordering and presentation order (distinct)

**SRS-007-AMD-003-SHALL-010: Proof ordering.**
- The *proof ordering* of `evidence_refs` is always canonical, strictly ascending bytewise. It is the order the closure commits to (SRS-007-AMD-001 SHALL-002, SHALL-014).
- There is no other proof ordering in v2. The v1 `evidence_ordering` values (LEX, TEMPORAL, DECLARED) do not exist in v2.
- A verifier SHALL NOT sort `evidence_refs`. It SHALL reject a list that is not strictly ascending (`REJECTED(input_not_strictly_ascending)`).

**SRS-007-AMD-003-SHALL-011: Presentation order (optional).**
- `evidence_order` gives, optionally, the order in which a producer presents the references, for example temporal order. Its value is a permutation of 0 … n−1 that indexes `evidence_refs`.
- `ordering_metadata` describes that order.
- Both are `null` together, or both are present.
- A value that is not a permutation of 0 … n−1, or that is present without its partner, is `REJECTED(presentation_order)`.

**SRS-007-AMD-003-SHALL-012: Commitment status of presentation order.**
- `evidence_order` and `ordering_metadata` are members of the record. They are therefore **covered by `proof_hash` and `commitment`** (§3): altering either is detected as a hash mismatch.
- They are **not covered by `evidence_closure_root`**: the closure root depends only on the set of references.
- So two records with the same evidence set and different presentation orders have the same closure root and different proof hashes.
- A presentation order attests only that the producer presented the evidence in that order. It is not evidence that the order is true, for example that it is chronological. Verifiers SHALL NOT report it as such.

**SRS-007-AMD-003-SHALL-002: Closure consistency.** A verifier holding the record SHALL:
- check that `closure_size` equals the number of `evidence_refs`;
- recompute `closure_root(evidence_refs)` and compare it with `evidence_closure_root`.

The verdict is `REJECTED(size_mismatch)` or `REJECTED(root_mismatch)` as defined in SRS-007-AMD-001.

## 3. Hashes (D-23 avoided by construction)

**SRS-007-AMD-003-SHALL-003.**
- Let `C` be the canonical form of the stored record.
- `P_hash` = `C` with the `proof_hash` and `commitment` members omitted entirely.
- `P_commit` = `C` with only the `commitment` member omitted.
- `proof_hash` = SHA-256(`P_hash`).
- `commitment` = SHA-256(`"AX:PROOF:v2"` ‖ LE64(len(`P_commit`)) ‖ `P_commit`).

A verifier derives both payloads from the stored bytes by removing members. It SHALL NOT substitute placeholder values.

So both hashes are deterministic functions of the stored record. In `AX:PROOF:v1` they are not: they were computed while `commitment` held 32 zero bytes, and the stored record carries the real value (finding D-23).

## 4. Capacity and workspace

**SRS-007-AMD-003-SHALL-004: Workspace constant.** v2 producers and verifiers SHALL use a caller-provided workspace (SRS-007-SHALL-043 Option B) of at least:

```c
#define AX_PROOF_V2_WORKSPACE_MIN  74270  /* bytes */
```

This is the exact largest canonical size of an admissible v2 record (§2), derived from the schema bounds. The worst case is built from the following:

| Element | Worst case |
|---|---|
| `closure_size` | 1,024 |
| `evidence_refs` | 1,024 references |
| `evidence_order` | a full permutation |
| Strings | each at its byte limit, made of characters that escape to 2 bytes (`"` or `\`) |
| `ordering_metadata` | present |
| Enum strings | the longest admissible |
| `violation` | present |
| `ledger_seq` | 2^53 − 1 |
| `proof_hash` and `commitment` | both present |

The derivation is mechanical and reproducible: `SRS-007-AMD-003-workspace/proof_v2_size.py`, output in `worst-case.txt`. Sizes for smaller n:

| n | Worst-case bytes |
|---|---|
| 1 | 1,718 |
| 192 | 15,173 |
| 1,000 | 72,542 |

One buffer of this size suffices:
- `P_hash` and `P_commit` (§3) are obtained from the canonical form by removing members, so neither is longer than it;
- the verifier serialises one form at a time.

An implementation SHALL check at compile time that its buffer is at least `AX_PROOF_V2_WORKSPACE_MIN`. It SHALL reject a record whose canonical form exceeds the workspace with a capacity fault, never by truncation. If the schema bounds change, the constant SHALL be re-derived and versioned with them.

## 5. Legacy v1 recognition

**SRS-007-AMD-003-SHALL-005: What is v1 material.** A verifier SHALL classify by schema, never by trial:

| Input | Classification |
|---|---|
| A record whose `schema_version` is `AX:PROOF:v1`, or whose commitment tag is `AX:PROOF:v1` | v1 proof record |
| A v1 compliance report, or any closure root, Merkle proof or evidence list taken from a v1 proof record | v1 closure material (`AX:MERKLE:v1`) |
| A record whose `schema_version` is `AX:PROOF:v2` and whose `closure_alg` is `AX:MERKLE:v2` | v2 |
| A record whose `schema_version` is `AX:PROOF:v2` with `closure_alg` absent or any other value | `REJECTED(unknown_construction)` |
| Any other `schema_version` | `REJECTED(unknown_schema)` |

**SRS-007-AMD-003-SHALL-006: Treatment of v1 material.**
1. **v1 inclusion proofs:** `V1_PROOF_UNSOUND`, never VERIFIED (SRS-007-AMD-001 SHALL-011).
2. **v1 closure root with its full evidence list:** MAY be recomputed under SRS-007-AMD-001 Appendix A and reported as `V1_ROOT_RECOMPUTED`, with the duplicate and leaf-count caveat.
3. **`proof_hash` and `commitment`:** verified under the approved legacy profile of SRS-007-AMD-004. Its verdicts state hash consistency only, never provenance.
4. **No conversion:** v1 records SHALL NOT be converted, re-hashed, re-rooted or relabelled as v2. A v2 record MAY cite a v1 record by its ledger position and commitment as evidence. That citation does not make the v1 record v2.

## 6. Activation (cut-over) and rollback

Cut-over is an **explicit owner-approved activation decision, recorded on the ledger**. It is never inferred from a calendar date, a software version or the presence of v2 records.

**SRS-007-AMD-003-SHALL-007: Approval.**
- An activation SHALL be preceded by a written owner decision record.
- The decision record SHALL name the target versions (`AX:PROOF:v2`, `AX:MERKLE:v2`) and the producing component or components.
- Its SHA-256 is the `decision_ref`.

**SRS-007-AMD-003-SHALL-008: Durable version identification.**
- The activation is committed as an `AX:STATE:v1` *version activation* record. Its members are:
  - `activation_id`, unique and never reused;
  - `component`;
  - `from_version`: `AX:PROOF:v1`;
  - `to_version`: `AX:PROOF:v2`;
  - `closure_alg`: `AX:MERKLE:v2`;
  - `decision_ref`;
  - `config_hash`, the hash of the producer configuration enabling v2.
- Its ledger sequence number is `S_cut`.
- Every v2 record also names its own `schema_version` and `closure_alg` (SHALL-001). The version in force can therefore be determined from the ledger alone, with no external state.

**SRS-007-AMD-003-SHALL-009: Producers and verifiers.**
- For ledger sequence numbers above `S_cut`, a producer SHALL emit only `AX:PROOF:v2`. At or below `S_cut` it SHALL emit only v1.
- A verifier determines the expected version for each ledger position from the activation and rollback records preceding it:
  - a v1 proof record in a v2 window is `REJECTED(v1_after_cutover)`;
  - a v2 record in a v1 window is `REJECTED(v2_before_cutover)`.
- A chain with no activation record is entirely v1.
- An activation record without a `decision_ref` is invalid. It does not open a v2 window, and it is reported as `REJECTED(activation_unapproved)`.

**SRS-007-AMD-003-SHALL-013: Rollback.**
- Rollback SHALL also be an owner decision with its own `decision_ref`. It is committed as an `AX:STATE:v1` *version rollback* record naming the `activation_id` it ends and the version restored.
- From its sequence number the producer emits v1 again.
- Rollback never deletes, rewrites or relabels records: v2 records emitted inside the window remain valid v2 and are verified under v2 rules.
- A later re-activation is a new activation with a new `activation_id`.

## 7. Verdicts

The following verdicts are added to the SRS-007-AMD-001 SHALL-012 set at record level:
- `REJECTED(unknown_schema)`
- `REJECTED(v1_after_cutover)`
- `REJECTED(v2_before_cutover)`
- `REJECTED(activation_unapproved)`
- `REJECTED(presentation_order)`
- the legacy verdicts of SRS-007-AMD-004 (`V1_LEGACY_CONSISTENT`, `V1_LEGACY_HASH_MISMATCH`, `V1_LEGACY_COMMITMENT_MISMATCH`, `V1_LEGACY_STRUCTURE_INVALID`), which replace the provisional `V1_HASH_PROFILE_LEGACY` of v0.1

## 8. Conformance

Before acceptance, as SRS-007-AMD-001 requires:
- two implementations written independently from this text SHALL produce byte-identical record vectors. These cover canonical records, both hashes, closure consistency, every recognition row of SHALL-005, and the cut-over rules.
- The vectors reuse the `AX:MERKLE:v2` vector references.

## 9. Open decisions

1. The `AX:STATE:v1` payload format for version activation and rollback records. The member list is in SHALL-008 and SHALL-013, but the state-record schema is owned by its own specification.
2. Two-implementation record vectors (§8). These are to be produced once this text is approved.

Resolved in v0.2:
- D-23 (SRS-007-AMD-004);

- the workspace constant;
- activation and rollback by owner decision.
