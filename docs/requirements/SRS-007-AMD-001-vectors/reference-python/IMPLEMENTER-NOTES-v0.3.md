# Implementer notes, SRS-007-AMD-001 v0.3 (Python implementation)

Sources read: AMENDMENT.md and VECTOR-FORMAT.md only. Implementation: merkle_v2.py (Python 3 standard library, hashlib for SHA-256). Output: vectors-py.txt.

## Ambiguities, contradictions and underspecified points

1. SHALL-008 step 0 versus step 1b ("before any p_i is read"). Step 0 checks that every p_i is 32 bytes, which inspects every path element, yet step 1b says a path longer than 10 is rejected "before any p_i is read", and the bullet under SHALL-008 says verification shall not read beyond the supplied path length. Taken literally, step 0 already touches all p_i before 1b. Resolution: I treated step 0 as a check of element lengths only (metadata, not contents) and applied it first, as the order requires; "read" in step 1b is taken to mean reading p_i contents into the hash computation. Consequence: an 11-element path with a malformed element would report malformed_reference rather than path_too_long. No vector exercises this combination. The text should say whether step 0 may run over a path longer than 10.

2. Verdict for a successful construction. SHALL-012 says the verdict set "applies to construction ... alike", but VECTOR-FORMAT only prints a construction outcome for cases 10 to 12, all of which reject. It is not stated whether a successful closure_root is reported as VERIFIED. Resolution: my build-case helper would print VERIFIED on success, but no vector line depends on this.

3. Path generation preconditions. SHALL-007 defines PATH only for valid (m, n). It does not say whether path generation itself applies the SHALL-002 list checks or rejects an out-of-range m (with which reason). Resolution: make_path runs SHALL-002 checks then rejects m outside 0..n-1 as index_or_size. Vector 9 obtains its path as P(0,9), a valid call, then presents it with m = 9, so this choice does not affect output.

4. Producer sorting versus construction rejection. SHALL-014 says a producer computes the root over a sorted copy, while SHALL-002 says the construction rejects and never repairs, and VECTOR-FORMAT cases 10 and 11 say "build closure_root over list" unsorted input. Resolution: closure_root takes the list exactly as given and applies SHALL-002; sorting is the caller's (producer's) job, done when forming D_n. Cases 10 and 11 therefore reject with input_not_strictly_ascending.

5. Expected size N in cases 1 to 14. SHALL-016 says N comes from the carrying record, never from the proof, but VECTOR-FORMAT says N equals the proof's own n unless stated otherwise. For case 2 (proof n = 2, root of D_4) and case 4 (proof n = 8, root R9) this means N is not the size of the tree the root was computed for. Resolution: followed VECTOR-FORMAT literally (N = 2 and N = 8). With a "record" N of 4 or 9 those cases would instead give size_mismatch.

6. Requirement map versus actual outcomes. Section 8 lists vector 4 (wrong_size) under tree-size binding, but with N equal to the proof's n = 8, a 4-element path for n = 8 overruns at step 3 and the result is REJECTED(path_too_long), not a root binding failure. Likewise vector 1 (internal_node_as_leaf_short) rejects as path_too_short and vector 2 as root_mismatch, so domain separation is only the decisive check in vector 13. Not a contradiction in the algorithm, but the map overstates what vectors 1 and 4 isolate. Results are computed, not chosen.

7. Case 9 and step order. Index 9 with n = 9 fails step 1 (index_or_size) before step 1a; N = 9 so no conflict. Noted only to confirm step order.

8. Case 12 (n = 1025). SHALL-002 says checks run "so that nothing beyond N_MAX is read". The harness still requires building D_1025 to present it. Resolution: the list is generated by the harness; closure_root checks len first and reads no element. Result too_many_refs.

9. "k is the largest power of two strictly less than n" (SHALL-004/007). Unambiguous for n > 1; implemented as doubling from 1 while 2k < n.

10. Step 3 inner while loop. "while (fn & 1) = 0 and fn != 0" runs immediately after a left-sibling combine where fn may equal sn and be even; this matches RFC 9162 section 2.1.3.2. The outer shift after the inner loop is applied unconditionally, as written. Implemented exactly.

11. Hex and path printing. VECTOR-FORMAT says comma-separated hex with no spaces and "-" for an empty path; len= is the path length in elements. Implemented that way. ROOT for n = 0 is closure_root([]) with a 20-byte input.

12. Reference generation string. "AX:MERKLE:v2:vector" is taken as the 19 ASCII bytes with no terminator, followed by LE64(i), by analogy with TAG in section 3. VECTOR-FORMAT uses "||" while the amendment uses "‖"; treated as the same operator.

13. Appendix A input precondition. Appendix A applies to "a strictly ascending list" but does not say what happens otherwise, nor whether V1_ROOT applies the SHALL-002 checks or N_MAX. Resolution: v1_root performs no checks (it is only ever called on D_n here). The single-leaf case returns d_0 unhashed and the empty case 32 zero bytes, as written.

14. Case 14 uses V1_ROOT(D_4) under the v2 verifier. The outcome is root_mismatch; SHALL-017 record-level dispatch (unknown_construction) is out of scope for the vector set per SHALL-012, so it is not modelled.

15. "Lines carried over from v0.2 SHALL remain byte-identical" (section 7). I did not have v0.2 vectors, so I could not check this; all lines were generated fresh from the v0.3 text.
